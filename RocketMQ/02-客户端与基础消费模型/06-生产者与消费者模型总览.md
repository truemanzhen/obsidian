# 生产者与消费者模型总览

> 研究定位：先把 RocketMQ 5.5.0 里“客户端模型”“协议模型”“Broker 请求模式”这三层拆开，再决定往哪条实现链继续下钻。
> 关键源码：`client/src/main/java/org/apache/rocketmq/client/`、`client/.../MQClientInstance.java`、`client/.../DefaultMQProducerImpl.java`、`client/.../DefaultMQPushConsumerImpl.java`、`proxy/src/main/java/org/apache/rocketmq/proxy/grpc/v2/`
> 阅读建议：不要一上来只盯 `DefaultMQPushConsumerImpl` 或 `DefaultMQProducerImpl`；先分层，否则很容易把 legacy client、Proxy/gRPC、POP/PULL 混成同一件事。

## 先给结论

- RocketMQ 5.5.0 同时维护两套主要接入面：经典 Java Client 和 Proxy/gRPC。
- “Producer / Push / Pull / LitePull”描述的是经典 Java SDK 的本地对象模型。
- `PUSH_CONSUMER / LITE_PUSH_CONSUMER / SIMPLE_CONSUMER` 描述的是 5.x 协议侧消费者类型。
- `PULL / POP` 则是 Broker 侧消息请求模式，不等于客户端类型。
- 很多 5.x 新能力不是新写一套客户端，而是把 Topic 类型、请求模式、Ack/InvisibleTime、Assignment 这些语义显式建模了。

## 先把三层模型拆开

### 1. 本地对象模型：经典 Java Client

这一层的代表类是：

- `DefaultMQProducer`
- `DefaultMQPushConsumer`
- `DefaultMQPullConsumer`
- `DefaultLitePullConsumer`

它回答的是：

- 应用程序拿什么 API 发消息
- 消费者是回调式还是轮询式
- 客户端本地怎么组织线程、路由缓存、offset 存储

### 2. 协议模型：5.x Proxy / gRPC

这一层的代表对象在 `apache.rocketmq.v2` 协议和 Proxy 活动类里：

- `PUSH_CONSUMER`
- `LITE_PUSH_CONSUMER`
- `SIMPLE_CONSUMER`
- `SendMessageActivity`
- `ReceiveMessageActivity`
- `AckMessageActivity`

它回答的是：

- 协议暴露哪些显式能力
- 服务端是否参与负载均衡和校验
- `ReceiptHandle`、`InvisibleDuration`、`MessageGroup` 这些语义如何上行/下行

### 3. Broker 请求模式：PULL / POP

这一层的核心类是：

- `MessageRequestMode`
- `MessageRequestModeManager`
- `QueryAssignmentProcessor`
- `PullMessageProcessor`
- `PopMessageProcessor`

它回答的是：

- Broker 认为这个 topic+group 应该按哪种方式取消息
- assignment 结果里附带什么消费语义
- 后续是 offset 驱动还是 ack/revive 驱动

## 经典 Java Client 的四种主模型

| 模型 | 核心类 | 关键问题 | 后续笔记 |
|---|---|---|---|
| Producer | `DefaultMQProducer` / `DefaultMQProducerImpl` | 路由、重试、批量、事务 |  |
| PushConsumer | `DefaultMQPushConsumer` / `DefaultMQPushConsumerImpl` | Rebalance、长轮询、回调消费 |  |
| PullConsumer | `DefaultMQPullConsumer` | 手动拉取、手动维护 offset |  |
| LitePullConsumer | `DefaultLitePullConsumer` | `subscribe` / `assign` 双模式、poll 语义 | [[50-LitePullConsumer轻量级拉消费]] |

这里最容易误解的是：

- Push 不是 Broker 主动把消息推到客户端。
- Push 的本质仍然是客户端 pull，只是客户端内部自己做了长轮询、线程派发和回调封装。

## gRPC / Proxy 侧多了一套显式消费者分类

5.x 的协议面把消费者显式拆成：

- `PUSH_CONSUMER`
- `LITE_PUSH_CONSUMER`
- `SIMPLE_CONSUMER`

这不是对经典 Java SDK 类名的简单映射。

更准确地说：

- `PUSH_CONSUMER` 更接近传统 push 体验
- `SIMPLE_CONSUMER` 显式暴露 receive / ack / changeInvisibleDuration
- `LITE_PUSH_CONSUMER` 又会牵动 LiteTopic / LMQ / Lite 管理链

所以 5.x 的“新消费模型”很多时候是协议契约变化，不只是 SDK 包装变化。

## 运行时公共骨架并没有被拆散

经典 Java Client 虽然暴露了多种 API，但底层大量复用同一套骨架：

- `MQClientInstance`
- `MQClientAPIImpl`
- `RebalanceService`
- `PullMessageService`
- `OffsetStore`

这可以直接从 `MQClientInstance.start()` 和 `DefaultMQPushConsumerImpl.start()` 看出来。

所以 Producer / Consumer 的差异不在于“各有一套完全独立网络栈”，而在于：

- 发送端怎么选队列、重试、编码
- 消费端怎么 rebalance、拉取、确认、处理失败

## 消费模型至少有两条轴

### 轴一：应用侧交互方式

- 回调式：`MessageListenerConcurrently` / `MessageListenerOrderly`
- 轮询式：`pull()` / `poll()`
- 协议式：`receive` + `ack` + `changeInvisibleDuration`

### 轴二：Broker 侧请求模式

- `PULL`
- `POP`

这也是为什么你不能把这些词混用：

- `PushConsumer` 不是 `POP`
- `LitePullConsumer` 不是 `MessageRequestMode`
- `SimpleConsumer` 也不等于经典 `PullConsumer`

## 5.5.0 和旧认知的关键差异

如果按 4.x 口径去读 5.5.0，最容易漏掉四件事：

- Broker 可以通过 `QueryAssignmentProcessor` 参与 assignment，而不是只让客户端本地算。
- `MessageRequestModeManager` 把 `topic + group -> PULL/POP` 变成了显式持久化配置。
- Proxy/gRPC 把 `ReceiptHandle`、backoff、message group 等语义前移到了接入层。
- `TopicMessageType` 把 FIFO / DELAY / TRANSACTION / LITE 的约束从“靠约定”提升成 topic 属性与校验链的一部分。
