# 批量消息与批量消费

> 研究定位：把 RocketMQ 里的“批量”拆成三件完全不同的事：`MessageBatch`、`ProduceAccumulator`、消费侧一次拉多条/一次回调多条。
> 关键源码：`common/.../MessageBatch.java`、`client/.../DefaultMQProducer.java`、`client/.../ProduceAccumulator.java`、`client/.../MQClientAPIImpl.java`、`broker/.../SendMessageProcessor.java`、`client/.../PullAPIWrapper.java`
> 阅读建议：先看批量消息如何生成，再看协议如何发送，最后再看消费侧为什么只是“批量拉取/批量回调”，不是同一个概念。

## 先给结论

- RocketMQ 5.5.0 里“批量”至少有三层含义，不能混写。
- `MessageBatch` 是一个消息容器，它会把多条消息编码成一个请求体，并走 `SEND_BATCH_MESSAGE`。
- `ProduceAccumulator` 是客户端本地自动聚合器，它会在内存里攒消息，到阈值再批量发。
- 消费侧的 `pullBatchSize`、`consumeMessageBatchMaxSize`、`batchAck` 只是“一次取/一次处理/一次确认多条”，不表示 Broker 端原生存的就是一个 batch 对象。
- Broker 侧还区分普通 batch 和 `inner-batch`，这与 queue 类型和 `NEED_UNWRAP_FLAG` 有关。

## 先分三种“批量”

### 1. 手动批量：应用显式传 `Collection<Message>`

入口在 `DefaultMQProducer.send(Collection<Message>)`：

```java
return this.defaultMQProducerImpl.send(batch(msgs));
```

其中 `batch(msgs)` 会：

1. `MessageBatch.generateFromList(msgs)`
2. 对批内每条消息做 `Validators.checkMessage(...)`
3. 为每条消息和 batch 本身生成 uniqId
4. `msgBatch.setBody(msgBatch.encode())`

也就是说：

- 批量消息不是 Broker 侧自动猜出来的
- 而是客户端先把多条消息编码成一个 batch body 再发送

### 2. 自动批量：`ProduceAccumulator`

如果开启自动批量，客户端会通过 `ProduceAccumulator` 聚合消息：

- `holdMs`：最多等多久
- `holdSize`：单批最大字节数
- `totalHoldSize`：整个聚合器允许占用的总字节数

源码里它维护了两张表：

- `syncSendBatchs`
- `asyncSendBatchs`

以及两个守护线程：

- `GuardForSyncSendService`
- `GuardForAsyncSendService`

这说明自动批量不是 Broker 端能力，而是客户端本地攒批。

### 3. 消费侧批量：一次拉多条/一次回调多条

这层常见参数是：

- `pullBatchSize`
- `consumeMessageBatchMaxSize`
- POP 路径里的 `batchAck`

它们回答的是：

- 一次网络请求最多带回多少条
- 一次交给业务回调多少条
- 一次确认多少条

而不是：

- “这些消息在 CommitLog 里原本是一个 batch”

## `MessageBatch.generateFromList(...)` 的硬约束

这段源码本身就是批量消息的第一道边界：

```java
if (message.getDelayTimeLevel() > 0 || message.getDelayTimeMs() > 0 || message.getDelayTimeSec() > 0 || message.getDeliverTimeMs() > 0) {
    throw new UnsupportedOperationException("Delayed messages are not supported for batching");
}
if (message.getTopic().startsWith(MixAll.RETRY_GROUP_TOPIC_PREFIX)) {
    throw new UnsupportedOperationException("Retry Group is not supported for batching");
}
if (!first.getTopic().equals(message.getTopic())) {
    throw new UnsupportedOperationException("The topic of the messages in one batch should be the same");
}
if (first.isWaitStoreMsgOK() != message.isWaitStoreMsgOK()) {
    throw new UnsupportedOperationException("The waitStoreMsgOK of the messages in one batch should the same");
}
```

可以直接得出四个结论：

- 延迟消息不能走手动 batch。
- retry topic 不能走手动 batch。
- 同一批消息必须同 topic。
- 同一批消息必须有相同的 `waitStoreMsgOK`。

这也是为什么“RocketMQ 支持批量”不能不带前提地讲。

## 协议层确实有单独的 batch request code

客户端发请求时，`MQClientAPIImpl` 会根据消息类型选请求码：

```java
request = RemotingCommand.createRequestCommand(
    msg instanceof MessageBatch ? RequestCode.SEND_BATCH_MESSAGE : RequestCode.SEND_MESSAGE_V2,
    requestHeaderV2);
```

Broker 侧也单独注册了这个请求码：

- `RequestCode.SEND_BATCH_MESSAGE`
- `BrokerController.registerProcessor(RequestCode.SEND_BATCH_MESSAGE, sendMessageProcessor, ...)`

所以 `MessageBatch` 不是“普通消息发几次”这么简单，它在协议层就是单独分支。

## Broker 侧还区分 batch 和 inner-batch

`SendMessageProcessor` 处理 batch 时，先把请求体包装成 `MessageExtBatch`。

随后它还会判断：

```java
if (QueueTypeUtils.isBatchCq(Optional.of(topicConfig)) && MessageClientIDSetter.getUniqID(messageExtBatch) != null) {
    messageExtBatch.setSysFlag(... | MessageSysFlag.NEED_UNWRAP_FLAG);
    messageExtBatch.setSysFlag(... | MessageSysFlag.INNER_BATCH_FLAG);
    messageExtBatch.setInnerBatch(true);
}
```

然后走不同写入分支：

- `putMessages(messageExtBatch)`：普通 batch
- `putMessage(messageExtBatch)`：inner-batch

这说明 Broker 侧并不是只有一种“批量存储”。

更准确地说：

- 普通批量更像“一个请求带多条消息”
- `inner-batch` 还会影响 CQ 表达和消费侧解包方式

## 消费侧为什么还要单独处理 inner-batch

客户端 `PullAPIWrapper.processPullResult(...)` 会检查：

- `MessageSysFlag.INNER_BATCH_FLAG`

如果命中，就要对 inner-batch 做解包。

这说明：

- 不是所有批量消息到消费者手里都已经天然变成普通单条
- 某些 queue 类型下，客户端要参与解码/解包

所以把批量只理解成“生产者省网络包”是不完整的。

## 自动批量真正攒批的键是什么

`ProduceAccumulator` 不是无脑把所有消息拼一起。

它按 `AggregateKey` 聚合，核心约束仍要保证：

- topic 相容
- queue/发送方式相容
- 消息属性足够一致，最终可编码成合法 `MessageBatch`

守护线程会定期扫描 accumulation：

- sync 路径唤醒等待线程
- async 路径直接 `readyToSend()` 后触发发送

所以自动批量的本质是：

- 客户端内存里的聚合调度器
- 不是 Broker 的后处理能力

## “批量消费”不要和“批量消息”混为一谈

消费侧最常见的误解有两个：

- 一次回调给你 32 条，不代表生产者发的是一个 `MessageBatch`
- POP 的 `batchAck` 也不代表生产者走了批量发送协议

消费侧这几个量分别回答不同问题：

| 机制 | 回答的问题 |
|---|---|
| `pullBatchSize` | 一次最多从 Broker 拉多少条 |
| `consumeMessageBatchMaxSize` | 一次回调给业务多少条 |
| `batchAck` | 一次确认多少条 |
| `MessageBatch` | 生产者是否用一个 batch request 发送 |

## 研究时最值得继续追的边界

- 哪些 queue 类型会触发 `inner-batch` 而不是普通 batch。
- `putMessages(...)` 和 `putMessage(...)` 在存储侧对 batch 的落盘差异。
- inner-batch 解包后，消费统计和 offset 语义怎么映射。
- 自动批量在超时、失败重试、顺序消息场景下有哪些限制。
