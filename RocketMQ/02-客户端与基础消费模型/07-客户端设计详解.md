# 客户端设计详解

> 研究定位：把 5.5.0 经典 Java Client 从“Producer / Consumer API”拆到运行时骨架、后台线程、订阅装载、路由刷新、拉取执行与失败回投。
> 关键源码：`client/src/main/java/org/apache/rocketmq/client/impl/factory/MQClientInstance.java`、`client/src/main/java/org/apache/rocketmq/client/impl/consumer/DefaultMQPushConsumerImpl.java`、`client/src/main/java/org/apache/rocketmq/client/impl/consumer/RebalanceImpl.java`、`client/src/main/java/org/apache/rocketmq/client/impl/consumer/PullMessageService.java`
> 阅读建议：先看 [[06-生产者与消费者模型总览]]，再看 [[08-客户端Producer内部实现]]、[[10-Offset管理机制]] 和 [[09-客户端Rebalance实现]]。

## 先给结论

- RocketMQ 客户端不是“Producer 一套、Consumer 一套”彼此割裂的实现，而是都挂在 `MQClientInstance` 这个共享运行时上。
- 对 Consumer 来说，真正的骨架不是 `DefaultMQPushConsumer` 这个 API 壳，而是 `DefaultMQPushConsumerImpl + RebalanceImpl + PullMessageService + OffsetStore`。
- Push 模型在客户端内部仍然是“后台 pull/pop + 本地缓存 + 回调执行”，不是 broker 主动把业务消息 server push 到客户端。
- POP 并没有引入独立的经典 Java Client 类型；在 5.5.0 里它仍然落在 `DefaultMQPushConsumerImpl` 这条链上。
- “消费超过 group 默认重试上限就进死信”不能当成客户端总规则。经典链路是否进 DLQ 由 broker 在 `consumerSendMsgBack(...)` 时按 `retryMaxTimes` 判定，详见 。

## 先把对象边界划清

### API 层和实现层不是一回事

用户直接接触的通常是：

- `DefaultMQProducer`
- `DefaultMQPushConsumer`
- `DefaultMQPullConsumer`
- `DefaultLitePullConsumer`

真正干活的则是：

- `DefaultMQProducerImpl`
- `DefaultMQPushConsumerImpl`
- `DefaultMQPullConsumerImpl`
- `DefaultLitePullConsumerImpl`

再往下一层，这些实现又会共享：

- `MQClientInstance`
- `MQClientAPIImpl`
- `RebalanceService`
- `PullMessageService`
- `TopicRouteData` / `brokerAddrTable`

所以研究客户端时，更稳的切法不是“按 API 名字记类”，而是：

1. [[06-生产者与消费者模型总览]]共享运行时是谁
2. [[08-客户端Producer内部实现]]每类客户端把哪些职责挂进去
3. 后台线程如何驱动这些职责

## `MQClientInstance` 才是客户端运行时中枢

`MQClientInstance.start()` 的启动顺序非常关键：

```java
this.mQClientAPIImpl.start();
this.startScheduledTask();
this.pullMessageService.start();
this.rebalanceService.start();
this.defaultMQProducer.getDefaultMQProducerImpl().start(false);
```

这说明一个经典客户端实例起来后，底层会统一拥有几类能力：

- remoting 网络通道
- 定时路由刷新
- 定时心跳
- 定时 offset 持久化
- 拉取执行线程
- rebalance 线程

`startScheduledTask()` 里还明确挂了几类周期任务：

- `updateTopicRouteInfoFromNameServer()`
- `cleanOfflineBroker() + sendHeartbeatToAllBrokerWithLock()`
- `persistAllConsumerOffset()`
- `adjustThreadPool()`

所以经典客户端不是“调用 send / consume 时才临时做点事”，而是一个有自己后台调度系统的长活进程。

## Consumer 启动主线真正做了什么

`DefaultMQPushConsumerImpl.start()` 的顺序可以直接当研究主线：

```java
this.checkConfig();
this.copySubscription();
this.mQClientFactory = MQClientManager.getInstance().getOrCreateMQClientInstance(...);
...
this.offsetStore.load();
...
this.consumeMessageService.start();
this.consumeMessagePopService.start();
...
mQClientFactory.registerConsumer(..., this);
mQClientFactory.start();
...
this.updateTopicSubscribeInfoWhenSubscriptionChanged();
this.mQClientFactory.checkClientInBroker();
if (this.mQClientFactory.sendHeartbeatToAllBrokerWithLock()) {
    this.mQClientFactory.rebalanceImmediately();
}
```

把它翻成运行时语义，就是：

1. [[06-生产者与消费者模型总览]]校验参数
2. [[08-客户端Producer内部实现]]把订阅关系装进 `subscriptionInner`
3. 绑定共享 `MQClientInstance`
4. [[09-客户端Rebalance实现]]选定 offset 存储实现
5. [[10-Offset管理机制]]启动消费线程池
6. [[11-消费重试与死信队列]]注册自己到客户端实例
7. 拉起网络与后台线程
8. 刷新 topic 路由
9. 发心跳给 broker
10. 立即触发第一次 rebalance

也就是说：

- “启动消费”不是一条 RPC
- 而是一整套本地状态构造 + 远端注册 + 后台调度启动

## `copySubscription()` 揭示了经典消费的资源模型

`copySubscription()` 会把用户订阅装入 `rebalanceImpl.getSubscriptionInner()`。

在 clustering 模式下，它还会额外补一条：

```java
final String retryTopic = MixAll.getRetryTopic(this.defaultMQPushConsumer.getConsumerGroup());
SubscriptionData subscriptionData = FilterAPI.buildSubscriptionData(retryTopic, SubscriptionData.SUB_ALL);
this.rebalanceImpl.getSubscriptionInner().put(retryTopic, subscriptionData);
```

这意味着经典 PushConsumer 的订阅集合从来就不只包含“业务 topic”。

它还天然携带：

- 业务 topic 订阅
- `%RETRY%group` 订阅

这也是为什么你不能把“消费失败重试”理解成完全独立于客户端订阅模型之外的能力。

## Push 的执行本质仍然是 Pull / Pop 后台任务

`PullMessageService` 是经典客户端最容易被低估的后台线程之一：

```java
MessageRequest messageRequest = this.messageRequestQueue.take();
if (messageRequest.getMessageRequestMode() == MessageRequestMode.POP) {
    this.popMessage((PopRequest) messageRequest);
} else {
    this.pullMessage((PullRequest) messageRequest);
}
```

这段代码直接给出几个关键事实：

- 客户端内部统一消费请求抽象是 `MessageRequest`
- broker 请求模式只有 `PULL` / `POP`
- Push / POP 最终都要靠后台线程去实际执行网络拉取

所以：

- Push 不是 broker 直接推
- POP 也不是一个完全脱离旧骨架的新客户端
- 它们只是“请求组织方式”和“后续确认语义”不同

## `DefaultMQPushConsumerImpl` 里同时存在 pull 和 pop 两条执行路径

同一个实现类里同时有：

- `pullMessage(final PullRequest pullRequest)`
- `popMessage(final PopRequest popRequest)`

这点非常重要，因为它直接推翻两个常见误解：

- “POP 对应一个独立的 POP 客户端类型”
- “PushConsumerImpl 只处理传统 pull”

源码事实正好相反：

- 经典 Java Client 不存在独立的 POP 客户端类型
- POP 在 5.5.0 就落在 `DefaultMQPushConsumerImpl`

## PushConsumer 的真正工作流

把关键对象串起来，经典 PushConsumer 的执行主线更接近这样：

```text
subscription 装载
  -> 路由刷新
  -> heartbeat
  -> rebalance
  -> 生成 PullRequest / PopRequest
  -> PullMessageService 执行远端请求
  -> 消息进入 ProcessQueue / PopProcessQueue
  -> ConsumeMessageService 提交业务回调
  -> 成功则更新 offset 或 ack
  -> 失败则走 send-back 或 revive 语义
```

这里要特别注意：

- `ProcessQueue` 是“客户端本地缓存与流控状态”
- 不是 broker 上的队列对象

## `ProcessQueue` 的职责不是“暂存消息”这么简单

旧笔记常把 `ProcessQueue` 简化成一个缓存容器，但它实际承担了更多控制责任：

- 已拉未消费消息缓存
- 消费跨度控制
- 最后 pull / consume 时间戳
- dropped / locked 状态
- 顺序消费协作状态

这也是为什么 rebalance 时不是简单“换一批 queue”，而是要连带处理：

- 老 `ProcessQueue` 的 dropped
- offset 持久化
- 顺序锁释放
- 新 `PullRequest` 派发

## OffsetStore 是客户端状态机的一部分

`DefaultMQPushConsumerImpl.start()` 会按消息模型选择 offset 存储实现：

```java
case BROADCASTING:
    this.offsetStore = new LocalFileOffsetStore(...)
case CLUSTERING:
    this.offsetStore = new RemoteBrokerOffsetStore(...)
```

### 广播模式

`LocalFileOffsetStore` 默认落在：

```java
System.getProperty("user.home") + File.separator + ".rocketmq_offsets"
```

并最终写入：

```text
{clientId}/{group}/offsets.json
```

### 集群模式

`RemoteBrokerOffsetStore` 会：

- 优先读内存
- 内存没有时去 broker 查
- 定期把当前 offset 批量回写 broker

核心行为在：

```java
long brokerOffset = this.fetchConsumeOffsetFromBroker(mq);
this.updateOffset(mq, brokerOffset, false);
```

以及：

```java
this.updateConsumeOffsetToBroker(mq, offset.getOffset());
```

所以 offset 不是“消费完自动就有了”的黑盒字段，而是客户端显式维护的一层本地状态，再按模式落到本地文件或 broker。

## 消费线程池和拉取线程不是同一个层面

客户端至少有两套并行机制：

### 1. [[06-生产者与消费者模型总览]]拉取执行线程

- `PullMessageService`
- 负责把 `PullRequest` / `PopRequest` 变成远端请求

### 2. [[08-客户端Producer内部实现]]消费执行线程池

- `ConsumeMessageConcurrentlyService`
- `ConsumeMessageOrderlyService`
- `ConsumeMessagePopConcurrentlyService`
- `ConsumeMessagePopOrderlyService`

这意味着：

- 拉到消息不等于立刻进入业务回调
- 业务慢不一定是 broker 慢，也可能是本地消费线程池积压
- 客户端流控既可能发生在 pull 侧，也可能发生在业务执行侧

## Push 流控是客户端主动做的

`pullMessage(...)` 里会先检查：

- `cachedMessageCount`
- `cachedMessageSizeInMiB`
- `processQueue.getMaxSpan()`

超过阈值后，它不会继续无脑拉，而是：

```java
this.executePullRequestLater(pullRequest, PULL_TIME_DELAY_MILLS_WHEN_CACHE_FLOW_CONTROL);
```

所以“Push 模型实时性差”时，先别急着怀疑 broker，也要看客户端是不是已经因为本地缓存过高进入流控。

## Rebalance 不是客户端附属功能，而是消费骨架的中段

在 `DefaultMQPushConsumerImpl.start()` 末尾，第一次真正进入消费前，会先：

```java
this.mQClientFactory.sendHeartbeatToAllBrokerWithLock()
this.mQClientFactory.rebalanceImmediately()
```

也就是说消费启动的关键顺序是：

- 先把自己声明给 broker
- 再做 queue assignment
- 再派发 pull/pop 请求

这点和很多“先订阅、再自己开始拉”的抽象讲法不同。更准确地说：

- rebalance 是客户端进入可消费状态的必要前置步骤

详细展开见 。

## Producer 也共享同一套客户端底座

虽然本篇重点是 Consumer，但 Producer 也共用：

- `MQClientInstance`
- `MQClientAPIImpl`
- `topicRouteTable`
- `brokerAddrTable`

因此：

- Producer 发消息前的路由刷新
- Consumer 拉消息前的路由刷新

本质上都依赖同一份客户端运行时缓存。

这就是为什么同一进程里多个 producer / consumer group 经常会复用同一个 client instance。

## 客户端失败回投不要和 broker 最终分流混为一谈

`DefaultMQPushConsumerImpl` 的确有：

- `sendMessageBack(...)`

但它的角色是：

- 把失败消息回投给 broker

最终是进 `%RETRY%group` 还是 `%DLQ%group`，是在 broker 侧 `consumerSendMsgBack(...)` 判定。

所以这篇里只需要记一层结论：

- 客户端负责“回投”
- broker 负责“最终分流”

完整分析见 。

## 这篇要纠正的几个旧说法

- “RocketMQ Push 就是服务端主动推消息。”  
  经典 Java Client 本质仍是后台 pull/pop 驱动。

- “POP 对应单独的 POP 客户端类型。”  
  5.5.0 经典客户端里不存在这个类。

- “客户端启动就是创建对象后直接开始消费。”  
  实际要经过订阅装载、offset store 初始化、路由刷新、心跳和 rebalance。

- “消费超过 group 默认重试上限就一定进死信。”  
  经典链路最终由 broker 按 `retryMaxTimes` 判定，且 POP 不是这条路径。
