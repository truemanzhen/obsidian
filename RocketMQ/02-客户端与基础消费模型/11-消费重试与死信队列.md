# 消费重试与死信队列

> 研究定位：把“消费失败之后会发生什么”拆成经典 `sendMessageBack` 主线、POP revive 主线，以及 5.x proxy/gRPC 的重试策略暴露面。
> 关键源码：`client/.../DefaultMQPushConsumerImpl.java`、`broker/.../AbstractSendMessageProcessor.java`、`remoting/.../SubscriptionGroupConfig.java`、`remoting/.../GroupRetryPolicy.java`、`broker/.../PopReviveService.java`、`proxy/.../DefaultReceiptHandleManager.java`
> 阅读建议：一定把“经典 Java Client 重试”和“POP / SimpleConsumer 的 ack-invisible-revive 模型”分开看。

## 先给结论

- RocketMQ 5.5.0 里并不存在一条统一的“失败自动重试”实现，而是至少有三层语义。
- 经典 PushConsumer 的主线仍然是：`sendMessageBack -> %RETRY%group -> 超阈值进 %DLQ%group`。
- POP 的主线不是 `sendMessageBack`，而是 `ACK/CK -> revive log -> PopReviveService -> POP retry topic`。
- `SubscriptionGroupConfig` 里虽然已经有 `GroupRetryPolicy`，但经典 `consumerSendMsgBack` 仍主要按 `retryMaxTimes + delayLevel(3 + reconsumeTimes)` 工作。
- `GroupRetryPolicy` 在 5.5.0 里更明确地影响的是 proxy/gRPC 一侧的 backoff 与 receipt renew/stop-renew 逻辑，而不是把经典 send-back 全部替换掉。

## 经典重试链路：客户端回投 broker

经典 PushConsumer 失败后会走：

```text
业务回调失败
  -> DefaultMQPushConsumerImpl.sendMessageBack(...)
  -> broker consumerSendMsgBack(...)
  -> 写入 %RETRY%<group>
  -> 超过最大重试次数后转入 %DLQ%<group>
```

客户端入口在 `DefaultMQPushConsumerImpl`：

```java
this.mQClientFactory.getMQClientAPIImpl().consumerSendMessageBack(...)
```

如果远端回投失败，它还会退化成本地重新发一条普通消息到 retry topic：

```java
Message newMsg = new Message(MixAll.getRetryTopic(this.defaultMQPushConsumer.getConsumerGroup()), msg.getBody());
newMsg.setDelayTimeLevel(3 + msg.getReconsumeTimes());
```

所以经典链路的第一性原理是：

- 失败消息重新包装
- 投给 `%RETRY%group`
- 由后续拉取消费重进业务回调

## Broker 怎么决定进 Retry 还是 DLQ

`AbstractSendMessageProcessor.consumerSendMsgBack(...)` 的关键分支是：

```java
String newTopic = MixAll.getRetryTopic(requestHeader.getGroup());
...
int maxReconsumeTimes = subscriptionGroupConfig.getRetryMaxTimes();
...
if (msgExt.getReconsumeTimes() >= maxReconsumeTimes || delayLevel < 0) {
    newTopic = MixAll.getDLQTopic(requestHeader.getGroup());
    queueIdInt = randomQueueId(DLQ_NUMS_PER_GROUP);
}
```

这里有几个要点：

- 经典主线看的是 `retryMaxTimes`。
- DLQ queue 数量固定是 `DLQ_NUMS_PER_GROUP = 1`。
- 没有超过阈值时，broker 仍按 delay level 投进 retry topic。
- 如果客户端请求头里带了 `maxReconsumeTimes`，在新版本协议下还可能覆盖 group 默认值。

所以“死信”不是客户端判定的，而是 broker 在 send-back 时做的 topic 分流。

## 经典延迟策略仍然是老语义

经典客户端和 broker 两端都还能看到兼容旧 delay level 的逻辑：

```java
delayLevel = 3 + msgExt.getReconsumeTimes();
```

以及客户端 fallback 里的：

```java
newMsg.setDelayTimeLevel(3 + msg.getReconsumeTimes());
```

这说明：

- 经典 retry 并没有完全切换到 `GroupRetryPolicy.nextDelayDuration(...)`
- 它的主干仍然延续老版本 delay level 兼容策略

这点非常重要，因为仅凭 `SubscriptionGroupConfig` 里多了策略对象，并不能推出经典 retry 主线已经全面改造。

## `GroupRetryPolicy` 存在，但别误读它的覆盖面

`SubscriptionGroupConfig` 的确已经挂了：

- `retryMaxTimes`
- `groupRetryPolicy`

而 `GroupRetryPolicy` 又分成：

- `CustomizedRetryPolicy`
- `ExponentialRetryPolicy`

对应实现：

```java
public RetryPolicy getRetryPolicy() {
    if (GroupRetryPolicyType.EXPONENTIAL.equals(type)) { ... }
    else if (GroupRetryPolicyType.CUSTOMIZED.equals(type)) { ... }
    else { return DEFAULT_RETRY_POLICY; }
}
```

但源码对照后要特别写清：

- 经典 `consumerSendMsgBack(...)` 直接读取的是 `retryMaxTimes`
- 经典 delay 仍主要用 `delayLevel`
- `GroupRetryPolicy` 在 5.5.0 更明确地出现在 proxy/gRPC 配置与 receipt 管理链路

例如：

- `GrpcClientSettingsManager` 会把 `GroupRetryPolicy` 转成 gRPC backoff policy
- `DefaultReceiptHandleManager` 在 stop-renew 时会调用：

```java
RetryPolicy retryPolicy = subscriptionGroupConfig.getGroupRetryPolicy().getRetryPolicy();
retryPolicy.nextDelayDuration(messageReceiptHandle.getReconsumeTimes())
```

所以更准确的结论是：

- “策略对象能力已经建模”
- 但“经典 Java 客户端 send-back 主线已完全按新策略执行”这个结论并不成立

## POP 的重试链路是另一套系统

POP 不走经典 `sendMessageBack`。

它的失败 / 超时恢复路径是：

```text
POP 返回消息
  -> ACK / ChangeInvisibleTime / 未 ACK
  -> revive log 记录 CK/ACK
  -> PopReviveService 扫描
  -> 重投到 POP retry topic
```

关键对象：

- `PopMessageProcessor`
- `AckMessageProcessor`
- `ChangeInvisibleTimeProcessor`
- `PopReviveService`
- `KeyBuilder.buildPopRetryTopic(...)`

这条链路里，“失败”不再等价于“客户端显式 send back 一条消息”，而是：

- 未 ACK 到期
- 或续期结束后仍未确认
- 最后由 broker 后台补偿线程做重投

## POP retry topic 和经典 retry topic 不是一回事

POP 重试 topic 由 `KeyBuilder` 构造：

```java
buildPopRetryTopicV1(topic, group) -> %RETRY%group_topic
buildPopRetryTopicV2(topic, group) -> %RETRY%group+topic
```

这与经典：

```java
MixAll.getRetryTopic(group) -> %RETRY%group
```

不是同一个资源模型。

区别在于：

- 经典 retry topic 只按 group 维度
- POP retry topic 同时编码了 group 和原 topic

这也是为什么 POP 可以在正常 topic 和对应 retry topic 之间做更细粒度的调度。

## POP 超时后的“重试”本质上是重投

`PopReviveService.reviveRetry(...)` 的核心是：

```java
msgInner.setTopic(KeyBuilder.buildPopRetryTopic(popCheckPoint.getTopic(), popCheckPoint.getCId(), ...));
...
if (popCheckPoint.isSuspend()) {
    msgInner.setReconsumeTimes(messageExt.getReconsumeTimes());
} else {
    msgInner.setReconsumeTimes(messageExt.getReconsumeTimes() + 1);
}
```

这说明 POP 下的“重试次数”增长不是靠客户端 send-back，而是由 revive 重投时推进。

所以你在文档里必须把下面两句话分开：

- 经典 retry：消费失败后回投 retry topic
- POP retry：消息超时后由 revive 重投到 pop retry topic

它们的触发点、参与对象、topic 设计都不同。

## 5.x proxy / gRPC 又多了一层显式策略暴露

5.x proxy/gRPC 会把 group 级重试策略显式暴露给客户端。

`GrpcClientSettingsManager` 里：

- `setMaxAttempts(groupConfig.getRetryMaxTimes() + 1)`
- 再按 `GroupRetryPolicyType` 生成 customized 或 exponential backoff

这说明在 5.x 协议侧，retry 不再只是 broker 内部行为，而是协议契约的一部分。

所以如果后续你要给同事解释“5.5.0 的重试能力”，最稳妥的分层方式是：

1. 经典 remoting Java Client
2. POP / revive
3. proxy / gRPC settings 与 receipt renew

## 这篇要纠正的几个旧说法

- “RocketMQ 的消费重试就是 sendMessageBack。”  
  这只对经典 PushConsumer 主线成立。

- “有了 `GroupRetryPolicy`，经典 retry 已经全部走新策略对象。”  
  源码对照不支持这个结论；经典链路仍主要是 `retryMaxTimes + delayLevel`。

- “POP 的重试就是 `%RETRY%group`。”  
  POP 使用 `buildPopRetryTopic(...)`，topic 语义不同。

- “DLQ 是客户端主动投进去的。”  
  经典主线里是 broker 在 `consumerSendMsgBack(...)` 时分流进去。

## 研究时建议继续核对的问题

- `SubscriptionGroupConfig.groupRetryPolicy` 除了 proxy/gRPC 之外，在 broker 经典链路还有没有新的接入点。
- POP 超过高次数重投后，业务侧真正感知到的是重试 topic 继续被消费，还是由上层 ack/receipt 语义拦住。
- `%RETRY%group` 和 POP V1/V2 retry topic 在监控、运维工具里分别如何暴露。
- namespace 参与后，retry / DLQ / pop retry 的资源名分别怎样编码，见 。
