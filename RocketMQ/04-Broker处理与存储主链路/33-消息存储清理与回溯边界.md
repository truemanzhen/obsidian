# 消息存储清理与回溯边界

> 研究定位：回答“为什么 offset 看起来合法，但历史消息已经读不到了”，并把 CommitLog 清理、ConsumeQueue 裁剪和 `nextBeginOffset` 修正连成一条线。
> 关键源码：`store/.../DefaultMessageStore.java`、`store/.../queue/ConsumeQueueStore.java`、`store/.../index/IndexService.java`
> 阅读建议：把“逻辑 offset 还在不在”和“物理消息还在不在”分开理解，再来看 broker 为什么会纠偏。

## 先给结论

- RocketMQ 的历史回溯能力只在“当前仍保留的数据窗口”内成立，不存在无限历史回放。
- 真实下界不是你手里保存的旧 offset，而是当前队列的 `minOffset`。
- CommitLog 先删，ConsumeQueue 和 Index 再按新的最小物理位点跟着裁剪，所以逻辑索引窗口不会早于物理窗口。
- `DefaultMessageStore.getMessage(...)` 不会只返回“读不到”，它会连同 `status / minOffset / maxOffset / nextBeginOffset` 一起告诉客户端怎么修正。
- TieredStore、冷数据控制会改变读取成本与路径，但不会推翻“本地有效窗口以当前 min/max offset 为准”这条基本事实。

## 真正的读取边界在哪里

`DefaultMessageStore.getMessage(...)` 一开始就取：

```java
minOffset = consumeQueue.getMinOffsetInQueue();
maxOffset = consumeQueue.getMaxOffsetInQueue();
```

随后按请求 offset 分四类：

```java
if (maxOffset == 0) { ... }
else if (offset < minOffset) {
    status = GetMessageStatus.OFFSET_TOO_SMALL;
    nextBeginOffset = nextOffsetCorrection(offset, minOffset);
} else if (offset == maxOffset) {
    status = GetMessageStatus.OFFSET_OVERFLOW_ONE;
} else if (offset > maxOffset) {
    status = GetMessageStatus.OFFSET_OVERFLOW_BADLY;
    nextBeginOffset = nextOffsetCorrection(offset, maxOffset);
}
```

这段代码直接说明：

- broker 判断合法性的基准是当前 `minOffset/maxOffset`
- 不是你本地记住的历史 offset

所以“旧 offset 还保存着”不代表“旧消息还存在且可读”。

## 清理顺序是两段式

### 第一段：先删 CommitLog

`DefaultMessageStore.CleanCommitLogService.deleteExpiredFiles()` 会按以下条件触发删除：

- 到时间了
- 磁盘使用超阈值
- 手工触发

真正执行点是：

```java
commitLog.deleteExpiredFile(fileReservedTime, ...)
```

所以物理消息是否还存在，首先取决于 CommitLog 的保留窗口。

### 第二段：再裁剪 ConsumeQueue / Index

`ConsumeQueueStore.CleanConsumeQueueService.deleteExpiredFiles()` 会拿当前：

```java
long minOffset = messageStore.getCommitLog().getMinOffset();
```

然后对所有 consume queue 做：

```java
deleteExpiredFile(logic, minOffset);
messageStore.getIndexService().deleteExpiredFile(minOffset);
```

这说明：

- ConsumeQueue 的删除依据不是自己的时间，而是 CommitLog 的最小物理 offset 已经前移
- Index 也跟着同一物理下界裁剪

因此逻辑索引窗口始终受制于物理消息窗口。

## 为什么“逻辑 offset 还像合法”但还是读不到

因为逻辑 offset 的合法性不是抽象数学意义上的“非负整数”，而是“位于当前 queue 的 `[minOffset, maxOffset]` 窗口”。

一旦队列头部已经被裁剪：

- 旧 offset 仍可能是你业务系统里保存的值
- 但在 broker 看来已经小于当前 `minOffset`

于是就会得到：

- `OFFSET_TOO_SMALL`
- `nextBeginOffset = minOffset`

这也是为什么客户端体验像“被纠偏”而不是“单纯抛错”。

## 读取时除了 offset 边界，还有物理消息缺口

即使 offset 在窗口内，`getMessage(...)` 仍可能因为对应物理消息拿不到而发生修正。

例如：

```java
SelectMappedBufferResult selectResult = this.commitLog.getMessage(offsetPy, sizePy);
if (null == selectResult) {
    status = GetMessageStatus.MESSAGE_WAS_REMOVING;
    nextPhyFileStartOffset = this.commitLog.rollNextFile(offsetPy);
}
```

这说明 broker 还要处理：

- consume queue 条目还在
- 但对应 commitlog 文件正在删除或已经不可用

所以“窗口内”也不保证每一条映射都一定顺滑命中。

## `nextBeginOffset` 为什么这么重要

`getMessage(...)` 最终会把这些信息统一塞回结果：

```java
getResult.setStatus(status);
getResult.setNextBeginOffset(nextBeginOffset);
getResult.setMaxOffset(maxOffset);
getResult.setMinOffset(minOffset);
```

这意味着 broker 的设计目标不是“报错结束”，而是：

- 告诉客户端当前窗口上下界
- 给出下一次应该从哪里继续拉

所以你研究消费回溯时，不能只看返回状态，还必须看：

- `nextBeginOffset`
- `minOffset`
- `maxOffset`

## recovery 过程也会把下界纠回当前物理窗口

恢复阶段 `DefaultMessageStore.recover(...)` 和 `recoverTopicQueueTable()` 会基于：

- `commitLog.getMinOffset()`
- `consumeQueueStore.recoverOffsetTable(minPhyOffset)`

重新修正 topic-queue offset 表。

还有这一段很关键：

```java
if (maxPhysicalPosInLogicQueue < this.commitLog.getMinOffset()) {
    maxPhysicalPosInLogicQueue = this.commitLog.getMinOffset();
}
```

它说明就算是恢复场景，系统也会主动把逻辑分发起点抬到当前物理窗口内，而不是坚持保留已经不可能恢复的数据。

## 回溯能力真正受哪些因素限制

### 1. CommitLog 保留窗口

这是根本约束。物理消息删了，历史回溯就不成立。

### 2. [[30-ReputMessageService异步分发]]ConsumeQueue 当前最小逻辑 offset

客户端能否从“最早消息”开始，不看 `0`，看的是 `consumeQueue.getMinOffsetInQueue()`。

### 3. [[31-刷盘机制]]Index 当前可用窗口

索引同样会被 `deleteExpiredFile(minOffset)` 裁剪，所以基于 key 的历史定位也受相同物理下界约束。

### 4. [[55-RocksDB集成设计]]冷数据与分层读取

冷数据仍可能存在，但读取路径可能转向：

- TieredStore
- 冷数据流控

这会影响读取成本、时延和流控体验，但不会改变 broker 返回当前 `min/max offset` 的基本边界。

## 这篇要纠正的几个旧说法

- “最早消费位点不是固定 0。”  
  更准确是从当前仍保留窗口里的 `minOffset` 开始。

- “CommitLog 删除后，ConsumeQueue 还能长期保留历史索引。”  
  `CleanConsumeQueueService` 会以 commitlog 最小物理 offset 为基准继续裁剪。

- “读不到旧消息说明 offset 丢了。”  
  很多时候 offset 没丢，只是已经落在当前窗口之外，被 broker 纠偏。

- “TieredStore 打开后，本地窗口边界就不重要了。”  
  读取路径会变化，但 broker 仍然按当前 queue 的有效窗口返回状态与修正点。
