# 存储架构总览

> 研究定位：先建立 RocketMQ 默认存储引擎的主骨架，再分别下钻 CommitLog、ConsumeQueue、Index、刷盘、清理和回溯边界。
> 关键源码：`store/src/main/java/org/apache/rocketmq/store/DefaultMessageStore.java`、`CommitLog.java`、`ConsumeQueue.java`、`index/IndexService.java`

## 先给结论

- 默认存储主链仍然是 `CommitLog -> Reput/Dispatch -> ConsumeQueue/Index`。
- 但 5.5.0 的 store 不再只是“三个文件”这么简单，它外围还有刷盘、HA、清理、恢复、冷数据和可选存储后端。
- `CommitLog` 是事实数据源，`ConsumeQueue` 是按 topic-queue 组织的逻辑消费索引，`IndexFile` 是按 key 的辅助索引。
- 真正的系统入口是 `DefaultMessageStore`，不是单个文件类。

## 先把主骨架看清

`DefaultMessageStore` 持有并编排至少这些核心对象：

- `CommitLog`
- `ConsumeQueueStore`
- `IndexService`
- `FlushManager`
- `HAService`
- 清理服务
- 恢复流程

在启动加载阶段，源码主线很明确：

```java
result = this.commitLog.load();
result = result && this.consumeQueueStore.load();
result = result && this.indexService.load(lastExitOK);
this.recover(lastExitOK);
```

这说明 store 的初始化顺序不是平铺的，而是：

1. 先有物理日志
2. 再有逻辑索引
3. 再做恢复与对齐

## 三个核心持久化对象

### 1. CommitLog

职责：

- 顺序追加写入完整消息
- 作为恢复、刷盘、HA 的事实来源

你可以把它理解成：

- 全局物理日志
- 默认存储引擎的真相源

### 2. ConsumeQueue

职责：

- 以 `topic + queueId` 维度组织消费索引
- 把逻辑 offset 映射到 commitlog 物理位点

它解决的是：

- 消费者不能在全局混写日志里直接按队列线性消费

### 3. IndexFile / IndexService

职责：

- 支持按 key / uniqKey 的辅助定位

它不是主消费路径的必要部分，但对按 key 查消息很关键。

## 主数据流

默认主数据流可以压缩成：

1. 写入 `CommitLog`
2. `ReputMessageService` 读新的 commitlog 区间
3. 分发到 `ConsumeQueue` / `Index`
4. 消费时先查 `ConsumeQueue`
5. 再回跳到 `CommitLog` 读完整消息

这也是 RocketMQ 常见的“顺序写 + 索引读”设计。

## 不要把它误读成“只有三个文件”

如果只记住三类文件，会漏掉 5.5.0 里很多关键边界：

- 刷盘是独立管理链
- HA 是独立复制链
- 清理和回溯修正有单独服务
- 恢复过程会重新对齐逻辑索引和物理日志
- TieredStore / RocksDB / CompactionStore 会改变部分存储后端

所以更准确的说法是：

- 三个文件是默认主链的核心持久化结构
- 不是整个 store 子系统的全部

## 为什么 CommitLog 仍然是中心

从恢复、清理、回溯边界看，很多关键判断都回到 commitlog：

- `recover(...)`
- `truncateDirtyFiles(...)`
- `getMessage(...)`
- `deleteExpiredFiles(...)`

这说明逻辑索引虽然重要，但最终边界仍由物理日志决定。

## 最值得记住的几个边界

- `ConsumeQueue` 的合法窗口受 `CommitLog` 保留窗口约束。
- `IndexFile` 只是辅助索引，不是消息存在性的最终判断依据。
- 存储层“读不到历史消息”常常不是 offset 丢了，而是窗口已经被清理和纠偏。
