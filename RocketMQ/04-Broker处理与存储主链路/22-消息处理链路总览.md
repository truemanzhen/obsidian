# 消息处理链路总览

> 研究定位：把“客户端请求怎么一路走到 Broker/store”拉成一条完整主线，重点看边界，不平均铺开所有类。
> 关键源码：`proxy/src/main/java/org/apache/rocketmq/proxy/grpc/v2/`、`proxy/src/main/java/org/apache/rocketmq/proxy/processor/`、`broker/src/main/java/org/apache/rocketmq/broker/processor/`

## 先给结论

- Proxy/gRPC 链路至少经历三次翻译：协议对象翻译、业务语义翻译、Broker 协议翻译。
- `GrpcMessagingApplication` 是入口，`MessagingProcessor` 是接入层和后端处理层的边界。
- `DefaultGrpcMessagingActivity` 不是业务终点，它只是把不同请求分发给具体 `Activity`。
- 真正写存储、做 POP、做 ack 的，不在 gRPC 入口类里，而在 `MessagingProcessor` 后面的 processor 与 Broker 处理器层。

## 先分四层

### 1. 接入入口层

核心对象：

- `GrpcMessagingApplication`
- `RequestPipeline`
- gRPC Interceptor

它回答：

- 请求怎么入站
- 上下文如何初始化
- 线程池如何隔离

### 2. Activity 分发层

核心对象：

- `DefaultGrpcMessagingActivity`
- `SendMessageActivity`
- `ReceiveMessageActivity`
- `AckMessageActivity`
- `RouteActivity`
- `ClientActivity`

它回答：

- 这是什么语义的请求
- 需要哪些参数校验
- 需要把 protobuf 转成什么内部对象

### 3. Proxy 处理层

核心对象：

- `MessagingProcessor`
- `ProducerProcessor`
- `ConsumerProcessor`
- `ClientProcessor`
- `TransactionProcessor`

它回答：

- 请求该发往哪个 Broker
- 用哪种协议访问 Broker
- 收到结果后如何回传

### 4. Broker 处理与存储层

核心对象：

- `SendMessageProcessor`
- `PullMessageProcessor`
- `PopMessageProcessor`
- `AckMessageProcessor`
- `CommitLog` / `ConsumeQueue`

它回答：

- Broker 怎么落盘
- Broker 怎么出队
- POP / PULL / ACK 怎么闭环

## 发送和消费在什么地方分叉

两条主线都共用：

- gRPC Interceptor
- `RequestPipeline`
- `GrpcMessagingApplication`
- `DefaultGrpcMessagingActivity`

真正分叉发生在具体 `Activity`：

- 发送走 `SendMessageActivity`
- 接收走 `ReceiveMessageActivity`
- ack 走 `AckMessageActivity`
- 延长不可见时间走 `ChangeInvisibleDurationActivity`

所以“发送链路”和“消费链路”不是两套完全独立栈，而是在 Activity 层之后才明显分流。

## 发送主线

发送请求大致会经过：

1. `GrpcMessagingApplication.sendMessage(...)`
2. `DefaultGrpcMessagingActivity.sendMessage(...)`
3. `SendMessageActivity.sendMessage(...)`
4. `MessagingProcessor.sendMessage(...)`
5. `ProducerProcessor`
6. Broker `SendMessageProcessor`
7. `CommitLog`

其中 `SendMessageActivity` 负责：

- topic 校验
- message/property 构造
- queue 选择
- gRPC 响应转换

## 消费主线

5.5.0 gRPC `receiveMessage(...)` 走的是 POP 语义，而不是经典 pull 语义直接透传。

大致路径是：

1. `GrpcMessagingApplication.receiveMessage(...)`
2. `DefaultGrpcMessagingActivity.receiveMessage(...)`
3. `ReceiveMessageActivity.receiveMessage(...)`
4. `MessagingProcessor.popMessage(...)` 或 `popLiteMessage(...)`
5. Broker `PopMessageProcessor`
6. 后续 ack / revive / invisibleTime 闭环

这也是为什么 `receiveMessage` 要和 `ackMessage`、`changeInvisibleDuration` 连起来看。

## `AbstractMessagingActivity` 的意义

`SendMessageActivity` 和 `ReceiveMessageActivity` 不是各自重复造校验逻辑。

它们共用 `AbstractMessagingActivity` 里的：

- `validateTopic(...)`
- `validateConsumerGroup(...)`
- `validateTopicAndConsumerGroup(...)`
- `validateInvisibleTime(...)`

这说明 Activity 层的公共抽象不是“消息发送/消息消费”，而是“接入层公共校验”。

## 最容易混淆的边界

- `GrpcMessagingApplication` 不是消息处理器，它只是 gRPC 服务入口。
- `DefaultGrpcMessagingActivity` 不是存储层，它只是 Activity 路由器。
- `MessagingProcessor` 不是 Broker，它是 Proxy 里的后端处理抽象。
- `receiveMessage` 不是经典 push，它更接近 5.x 的 POP/gRPC 消费契约。
