# 事务消息设计

> 研究定位：把 RocketMQ 事务消息从“半消息 + 回查”的口号拆成完整实现链，回答 Broker 到底如何管理未决事务。
> 关键源码：`broker/src/main/java/org/apache/rocketmq/broker/transaction/queue/TransactionalMessageServiceImpl.java`、`TransactionalMessageBridge.java`、`TransactionalMessageCheckService.java`
> 阅读建议：这篇重点不在“两阶段提交”概念，而在 Broker 侧半消息、op 消息和回查线程如何配合。

## 先给结论

- RocketMQ 事务消息的核心不是在 CommitLog 里打个标记就结束，而是围绕半消息队列、op 队列和定时回查组成独立链路。
- 生产者 first phase 发送的是 half message，不会立刻进入普通消费主链。
- Broker 通过 op 消息记录 commit / rollback 决策，并周期性扫描未决 half message。
- 5.5.0 里事务相关的状态管理已经不只是简单内存逻辑，还包括事务 metrics 和可选 RocksDB 存储支线。

## half message 是什么

事务消息第一阶段写入的不是“普通可消费消息”，而是：

- half message

它的语义是：

- 已经进入 Broker 存储
- 但最终事务结果尚未确定
- 不能直接对消费者可见

所以 half message 的真正作用是：

- 为本地事务待确认状态提供持久化落点

## 事务消息主链

可以压缩成：

1. [[28-CommitLog写入流程]]生产者发送 prepared/half message
2. [[59-HA主从同步设计]]Broker 写入 half topic
3. [[39-消息撤回Recall设计]] [[39-消息撤回Recall设计]]应用执行本地事务
4. 生产者回传 commit / rollback
5. Broker 记录 op 并决定是否投递或清理
6. 未决消息由回查线程补偿

这说明 RocketMQ 事务消息不是“请求级同步事务”，而是：

- 存储持久化 + 最终一致补偿模型

## `TransactionalMessageServiceImpl` 在做什么

它的职责不是单一发送接口，而是整套事务中枢：

- 准备 half message
- 处理 commit / rollback
- 周期检查未决消息
- 管理 op 队列与消费位点

这篇真正应该记住的是：

- Broker 事务逻辑的核心入口就在这里

## 为什么还要有 op 队列

如果只有 half topic，Broker 只能知道“谁待确认”，但不知道“谁已经被 commit/rollback 了”。

所以还需要 op 队列来记录：

- 哪些 half message 已经有了最终操作

检查线程扫描时，会先构造：

- half 偏移
- op 偏移
- remove map

然后判断哪些 half 消息仍未完成。

## 回查线程到底查什么

`check(...)` 会遍历事务 half topic 对应的 message queue。

它会判断：

- 这条 half 消息是否已经有 commit/rollback 对应 op
- 是否超过检查阈值
- 是否已经老到可以跳过
- 是否需要重新 put back half queue
- 是否需要向生产者发起事务回查

这说明事务回查不是“随机抽查”，而是 Broker 对 half topic 的系统性扫描。

## `needDiscard` / `needSkip` 的边界

源码里两类判断很关键：

### `needDiscard`

如果回查次数超过上限，就可以丢弃。

### `needSkip`

如果消息年龄已经超过文件保留时间，也可以跳过。

这意味着事务消息并不是无限期未决：

- 它同样受检查次数和保留窗口约束

## 为什么要 `putBackHalfMsgQueue`

当 half message 需要继续保留待查状态时，Broker 会把它重新写回 half queue。

这不是重复写入 bug，而是事务未决状态延续的一部分。

所以事务消息里经常会看到：

- 新的 queueOffset
- 新的 commitLogOffset
- 新的 msgId

这和普通消息“一次写入固定不变”的直觉不同。

## commit / rollback 真正改变的是什么

Broker 收到事务结束请求后，不是简单改一位状态，而是通过：

- op 消息
- half 消息处理
- 最终投递或清理

来实现最终一致。

所以事务消息的“完成”不是内存状态迁移，而是：

- 一组消息记录与索引关系被补齐

## 5.5.0 比旧理解多了什么

- `TransactionMetrics`
- 可选 `TransactionalMessageRocksDBService`
- slave acting master 等复杂场景下的 escape 处理

这说明事务消息在 5.5.0 里已经不仅是“基础功能”，还要适应更复杂的 HA 与治理形态。

## 这篇最值得记住的误区纠正

### “事务消息就是普通消息加一个 prepared 标记”

不对。它有独立 half/op/check 链路。

### “commit 之后消息立刻天然可见”

更准确地说，是 Broker 通过事务链完成最终投递与可见性转换。

### “事务回查只是客户端行为”

不对。回查由 Broker 的事务检查服务驱动。
