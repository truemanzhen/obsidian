# 消息压缩机制

> 研究定位：把 RocketMQ 5.5.0 的压缩算法、`sysFlag` 编码和客户端/服务端解压职责拆开，回答“压缩到底发生在发送端还是 Broker 端”。
> 关键源码：`common/src/main/java/org/apache/rocketmq/common/compression/CompressorFactory.java`、`Lz4Compressor.java`、`ZstdCompressor.java`、`ZlibCompressor.java`、`common/message/MessageSysFlag`
> 阅读建议：这篇和 [[03-消息协议与类体系]] 连读，压缩信息最终会写进 `sysFlag`。

## 先给结论

- RocketMQ 5.5.0 支持至少三种压缩算法：`LZ4`、`ZSTD`、`ZLIB`。
- 压缩实现入口在 `CompressorFactory`，它只是按 `CompressionType` 返回具体实现。
- 压缩状态不会只存在于客户端内存，而是编码进消息 `sysFlag`。
- Broker 和消费端需要依据 `sysFlag` 决定如何解压消息体。

## `CompressorFactory` 的意义

这部分源码很直接：

```java
COMPRESSORS.put(CompressionType.LZ4, new Lz4Compressor());
COMPRESSORS.put(CompressionType.ZSTD, new ZstdCompressor());
COMPRESSORS.put(CompressionType.ZLIB, new ZlibCompressor());
```

它说明：

- 算法选择已经抽象成稳定接口
- 压缩能力不是硬编码单一实现

## 压缩语义不是普通属性，而是 `sysFlag`

压缩相关的关键状态通常包括：

- 是否压缩
- 压缩类型

这些信息不是简单存在 `properties`，而是进了 `sysFlag` 位图。

原因很简单：

- 解码链必须快速知道要不要解压
- 压缩算法类型也要在高频路径快速判断

## 为什么 5.5.0 要同时支持多算法

因为不同算法的取舍不同：

- `LZ4` 偏速度
- `ZSTD` 偏压缩率和综合表现
- `ZLIB` 更传统、兼容性更强

RocketMQ 把它们放进统一接口，说明它想提供的是：

- 可切换的压缩策略

而不是单一固定实现。

## 压缩发生在哪一侧

最准确的说法是：

- 压缩通常发生在发送侧
- Broker / 消费端依据 `sysFlag` 做对应处理

也就是说，Broker 不是“收到消息后统一帮你压一遍”的主角。

## 压缩和消息类型的关系

压缩不是一种独立消息类型，而是一种消息体编码优化。

所以它和：

- FIFO
- DELAY
- TRANSACTION

这些语义是正交的。

换句话说：

- FIFO 消息也可以压缩
- 延迟消息也可以压缩

## 和存储链的关系

一旦压缩状态写进 `sysFlag` 并编码落盘，后续：

- CommitLog 保存的就是压缩后的消息体
- 解码时再决定是否解压

所以压缩影响的是：

- 存储体积
- 网络传输
- 解码成本

## 哪些旧理解容易错

### “压缩是 Broker 存储层透明优化”

不够准确。它首先是消息编码层的明确语义。

### “压缩算法只和客户端相关”

不对。解码链和存储链都要理解 `sysFlag`。

### “压缩就是 GZIP”

不对。5.5.0 已显式支持 LZ4/ZSTD/ZLIB 多种实现。

## 这篇最值得记住的点

- 压缩能力被抽象为统一接口。
- 具体算法选择由 `CompressionType` 决定。
- 是否压缩以及压缩类型最终都进 `sysFlag`。
