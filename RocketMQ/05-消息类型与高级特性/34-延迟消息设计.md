# 延迟消息设计

> 研究定位：把 RocketMQ 的两条延迟路径拆开看清楚，回答“延迟消息到底是 topic 属性、定时任务，还是独立存储引擎”。
> 关键源码：`broker/src/main/java/org/apache/rocketmq/broker/schedule/ScheduleMessageService.java`、`store/src/main/java/org/apache/rocketmq/store/timer/TimerMessageStore.java`
> 阅读建议：这篇要和 [[41-延迟消息Store层]] 连读，前者看业务语义，后者看存储底座。

## 先给结论

- RocketMQ 5.5.0 里，延迟消息不是单一实现，而是“经典 delay level”与“Timer wheel/timer log”两条路径并存。
- 经典延迟消息本质上是把消息先写到系统延迟 topic，再由 `ScheduleMessageService` 到期转发回真实 topic。
- 新的 Timer 路径则是由 `TimerMessageStore`、`TimerWheel`、`TimerLog` 组成的独立存储与投递链。
- 延迟语义最终还是通过消息属性承载，例如 `PROPERTY_DELAY_TIME_LEVEL`、`PROPERTY_TIMER_DELIVER_MS`、`PROPERTY_TIMER_DELAY_MS`。

## 先把两条路径分开

### 1. [[41-延迟消息Store层]]经典 delay level

这是老路径，核心是：

- 消息先进入系统延迟 topic
- Broker 定时扫描延迟队列
- 到期后重新投递到真实 topic

源码上它主要落在：

- `ScheduleMessageService`

### 2. [[35-事务消息设计]]Timer message

这是 5.5.0 更细粒度的延迟实现。

它不是简单“定时转发”，而是一个完整的：

- timer log
- timer wheel
- enqueue / dequeue
- checkpoint

体系。

## 延迟消息的属性入口

延迟并不是单独字段，而是属性驱动。

常见属性有：

- `PROPERTY_DELAY_TIME_LEVEL`
- `PROPERTY_TIMER_DELAY_SEC`
- `PROPERTY_TIMER_DELAY_MS`
- `PROPERTY_TIMER_DELIVER_MS`

这说明用户侧写入的“延迟时间”最终会被转换成：

- Broker 能识别的系统属性

## 经典路径的核心思路

`ScheduleMessageService` 维护一张：

- `delayLevel -> delayTimeMillis`

然后定时扫描系统 schedule topic。

它的核心行为是：

1. [[41-延迟消息Store层]]读取延迟 topic 的消费队列
2. [[35-事务消息设计]]判断消息是否到期
3. 将消息重新投递回真实 topic

你可以把它理解成：

- “按 delay level 的重投递器”

## 为什么要单独用系统 topic

因为经典延迟消息本质上要先“暂存”。

所以 Broker 先把消息写到一个系统 topic，然后在到期后再恢复成原始 topic。

这就解释了为什么延迟消息链路里总会看到：

- 真实 topic
- 系统 schedule topic
- 二次投递

## Timer 路径为什么更独立

`TimerMessageStore` 不只是“定时器”，而是完整的存储与调度系统。

它内部核心对象有：

- `TimerWheel`
- `TimerLog`
- `TimerCheckpoint`

并且还有多条后台服务线程：

- enqueue get / put
- dequeue get / put
- warm service
- flush service

所以它不是经典 delay level 的简单增强，而是独立实现。

## 5.5.0 里应该怎么理解“延迟消息”

最稳妥的理解方式是分两层：

### 语义层

- “这条消息什么时候可见”

### 实现层

- 经典 path：schedule topic + 转发
- timer path：timer wheel + timer log + dequeue

## 经典路径的边界

`ScheduleMessageService` 会校正延迟 offset。

这说明延迟消息链路不是无限自增的：

- 它要和对应的 ConsumeQueue 物理窗口对齐

所以延迟消息也会遇到：

- offset 超前
- offset 落后
- 需要修正

## Timer 路径的边界

`TimerMessageStore` 里最重要的约束是：

- 精度
- wheel TTL
- checkpoint

如果 broker 停太久，timer wheel 会有消息损失风险。

这就是 Timer 路径和经典路径最大的运维差异：

- 经典路径更简单
- Timer 路径能力更强，但对状态一致性要求更高

## 哪些旧稿容易写错

### 1. [[41-延迟消息Store层]]把所有延迟消息都写成 delay level

不对。5.5.0 里 Timer 路径是独立的。

### 2. [[35-事务消息设计]]把延迟消息理解成消费者侧逻辑

不对。延迟投递由 Broker 负责。

### 3. 把定时转发和 timer wheel 混成一条链

不对。它们是两个实现层次。

## 这篇最值得记住的点

- 5.5.0 的延迟不是单一实现。
- 经典 delay level 和 Timer message 是两条不同路径。
- 真正的实现边界在 Broker 存储和调度，不在客户端。
