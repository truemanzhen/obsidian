# 冷数据消费控制

> 研究定位：把 RocketMQ 5.5.0 的冷数据控制拆成存储侧探测和 Broker 侧限流两层，回答“为什么读慢的消息要单独被管起来”。
> 关键源码：`broker/src/main/java/org/apache/rocketmq/broker/coldctr/ColdDataCgCtrService.java`、`ColdDataPullRequestHoldService.java`、`store/src/main/java/org/apache/rocketmq/store/CommitLog.java` 里的 `ColdDataCheckService`
> 阅读建议：这篇要和 [[33-消息存储清理与回溯边界]]、[[56-TieredStore分层存储]] 一起看，冷数据不是单一开关。

## 先给结论

- 冷数据控制的目标不是“禁读”，而是控制冷读对系统资源的冲击。
- 5.5.0 里它至少有两层：存储侧检查冷数据分布，Broker 侧决定是否挂起/放行拉取请求。
- `ColdDataCgCtrService` 负责 consumerGroup 维度的冷读统计、阈值和自适应策略。
- `ColdDataPullRequestHoldService` 负责把冷数据相关 pull request 暂挂后再放行。

## 为什么要做冷数据控制

冷数据通常意味着：

- 读取更慢
- 可能触发更重的存储路径
- 容易拖慢热数据消费链路

所以 Broker 需要单独把它看成一种流控对象，而不是普通消息读取。

## 存储侧：`ColdDataCheckService`

`CommitLog` 里有专门的 `ColdDataCheckService`。

它负责检查：

- 当前是否启用了 cold data flow control
- 相关扫描是否启用
- 当前数据块是否需要被标记为冷数据

这说明冷数据不是纯 Broker 侧概念，存储层也会参与判断。

## Broker 侧：`ColdDataCgCtrService`

它维护两张核心表：

- runtime table
- config table

以及一个全局累计值：

- `GLOBAL_ACC`

它会按 consumerGroup 统计冷读量，并按阈值决定是否需要控制。

### 关键逻辑

- 冷读累计到阈值，就可能触发控制
- 一段时间没有冷读，就会清理 runtime 记录
- 如果启用了自适应策略，还会动态升降阈值

这说明它不是简单的“阈值 if 判断”，而是带有自适应和生命周期管理的服务。

## Broker 侧：`ColdDataPullRequestHoldService`

这个服务负责的是：

- 把冷数据相关 pull request 暂时放进 hold queue
- 冷却一段时间后再通过 `PullMessageProcessor` 唤醒

所以它的角色不是拒绝请求，而是：

- 延后处理

这也是冷数据控制和普通限流最不同的地方。

## 为什么它分成两层

如果只在 Broker 侧做挂起：

- 你不知道冷数据从哪里来

如果只在存储侧做判断：

- 你不知道如何对外控制消费节奏

所以 5.5.0 的设计是：

- 存储侧识别冷
- Broker 侧调度冷读请求

## 自适应策略的意义

`ColdDataCgCtrService` 里有 PID / simple 两套策略入口。

这说明冷数据控制不是固定阈值就够了，它还要考虑：

- 热点变化
- 读流量波动
- 不同 consumerGroup 的差异

## 哪些旧理解容易错

### “冷数据控制就是把读请求拒绝掉”

不对。它更多是挂起和放行节奏控制。

### “冷数据只属于 TieredStore”

不够准确。它和分层存储相关，但控制逻辑在 Broker / store 都有参与。

### “冷数据控制就是一个配置项”

不对。它是一个服务体系。

## 这篇最值得记住的点

- 冷数据控制是存储侧检测 + Broker 侧调度的组合。
- `ColdDataCgCtrService` 管统计和策略。
- `ColdDataPullRequestHoldService` 管请求挂起和唤醒。
