# 命名空间与资源隔离

> 研究定位：厘清 RocketMQ 5.5.0 里的 namespace 到底是“资源名包装协议”，还是“真正的物理隔离边界”。
> 关键源码：`remoting/.../NamespaceUtil.java`、`client/.../ClientConfig.java`、`client/.../NamespaceRpcHook.java`、`client/.../MQClientAPIImpl.java`
> 阅读建议：先回答“资源名怎么包/怎么拆”，再看请求头扩展字段和回包去 namespace 的路径；不要把 namespace 直接等同于独立集群或独立存储。

## 先给结论

- RocketMQ 的 namespace 首先是资源命名隔离，不是独立 CommitLog、独立 ConsumeQueue、独立 Broker 集群。
- 核心机制是 `NamespaceUtil.wrapNamespace(...)` / `withoutNamespace(...)` 对 topic/group 名做包装与解包。
- retry / DLQ 资源不是 namespace 例外，而是“先保留特殊前缀，再处理 namespace”。
- 5.5.0 里还存在 `namespace` 和 `namespaceV2` 两条线：前者更多体现在本地资源改写，后者通过 `NamespaceRpcHook` 注入请求扩展字段。
- 所以 namespace 是“逻辑租户前缀 + 协议扩展标记”的组合，不是物理多租户。

## `NamespaceUtil` 才是这套机制的中心

最关键的方法就是这几个：

- `wrapNamespace(namespace, resourceWithoutNamespace)`
- `withoutNamespace(resourceWithNamespace)`
- `withoutNamespace(resourceWithNamespace, namespace)`
- `wrapNamespaceAndRetry(namespace, consumerGroup)`
- `getNamespaceFromResource(resource)`

从实现看，`NamespaceUtil` 明确做了三件事：

1. system resource 直接跳过
2. retry / DLQ 先拆前缀再处理
3. namespace 分隔符固定是 `%`

这已经说明：

- namespace 不是一套独立路由表
- 而是一套资源命名规则

## 普通 topic/group 与 retry/DLQ 的形态

普通资源：

- topic：`namespace%TopicA`
- consumer group：`namespace%GroupA`

特殊资源：

- retry：`%RETRY%namespace%GroupA`
- DLQ：`%DLQ%namespace%GroupA`

`withoutNamespace(...)` 的实现就是：

1. 先判断是否 retry / DLQ
2. 去掉 `%RETRY%` 或 `%DLQ%`
3. 再查第一个 `%` 作为 namespace 分隔点
4. 最后把前缀补回去

所以不能把 retry / DLQ 想成“namespace 外面完全另一套命名空间”。

## system resource 不会被随意包 namespace

`NamespaceUtil.isSystemResource(...)` 会检查：

- `TopicValidator.isSystemTopic(resource)`
- `MixAll.isSysConsumerGroup(resource)`

这意味着像系统 topic、系统 group 这类资源，默认不走普通 namespace 包装逻辑。

这也是 namespace 研究里很容易漏掉的边界：

- namespace 主要服务于业务资源
- 不是把所有字符串一律机械加前缀

## 客户端本地资源改写发生在哪里

`ClientConfig` 里保留了：

- `withNamespace(resource)`
- `withoutNamespace(resource)`
- `queueWithNamespace(...)`

虽然这些接口已标 `@Deprecated`，但 5.5.0 仍大量通过它们背后的 `NamespaceUtil` 工作。

例如：

- Producer 发送前会 `withNamespace(topic)`
- Consumer 初始化时会给 group 包 namespace
- 客户端从 Broker 拉回消息后会再 `withoutNamespace(...)`

典型位置包括：

- `DefaultMQPushConsumer.setConsumerGroup(...)`
- `DefaultMQPullConsumer.setConsumerGroup(...)`
- `DefaultLitePullConsumer.setConsumerGroup(...)`
- `DefaultMQProducerImpl` 里发送/回包后的 topic 还原
- `MQClientInstance` 路由回包中的 `queue.setTopic(...)`

这说明 namespace 不只影响发送请求，也影响客户端看到的返回值。

## `namespaceV2` 走的是请求扩展字段

这点很容易被写错。

5.5.0 里并不是 `RpcRequestHeader` 直接定义了显式 namespace 字段，而是：

- `NamespaceRpcHook` 在发请求前往 `RemotingCommand.extFields` 注入：
  - `MixAll.RPC_REQUEST_HEADER_NAMESPACED_FIELD = "nsd"`
  - `MixAll.RPC_REQUEST_HEADER_NAMESPACE_FIELD = "ns"`

对应代码：

```java
request.addExtField(MixAll.RPC_REQUEST_HEADER_NAMESPACED_FIELD, "true");
request.addExtField(MixAll.RPC_REQUEST_HEADER_NAMESPACE_FIELD, clientConfig.getNamespaceV2());
```

所以更准确的表述应该是：

- namespaceV2 通过 RPCHook 给请求打扩展标记
- 不是在所有 `RpcRequestHeader` 子类里都显式新增了同名 Java 字段

## Trace / Hook / 管理面经常会主动去 namespace

这也是 namespace 不是“应用永远看到完整物理名”的证据。

例如 trace hook 里会显式做：

- `NamespaceUtil.withoutNamespace(context.getProducerGroup())`
- `NamespaceUtil.withoutNamespace(msg.getTopic())`

也就是说很多观测/追踪场景，系统更愿意展示业务逻辑资源名，而不是带 namespace 的物理表达。

所以 namespace 研究一定要分清：

- 协议传输时的资源名
- 客户端 API 暴露给业务时的资源名
- Trace / Admin / Metrics 展示时的资源名

## namespace 能解决什么，不能解决什么

它能解决：

- 业务 topic/group 命名冲突
- 逻辑租户隔离
- 某些请求上下文里的租户透传

它不能直接保证：

- 独立存储
- 独立路由节点
- 独立 Broker 进程
- 独立 ACL / 配额 / 物理资源池

所以如果文档里把 namespace 直接写成“RocketMQ 多租户方案”，这句话必须带限定词：

- 它是逻辑命名层面的多租户
- 不是天然物理隔离方案
