# 消息协议与类体系

> 研究定位：把 RocketMQ 5.5.0 的消息对象、属性系统、编码版本和 Broker 内部消息形态串起来，回答“消息在不同层到底长什么样”。
> 关键源码：`common/src/main/java/org/apache/rocketmq/common/message/Message.java`、`MessageExt.java`、`MessageExtBrokerInner.java`、`MessageBatch.java`、`MessageDecoder.java`、`MessageVersion.java`、`MessageConst.java`
> 阅读建议：这篇不要只看字段名，要把“客户端对象”“Broker 内部对象”“CommitLog 编码格式”三层区分开。

## 先给结论

- RocketMQ 的消息模型不是单类模型，而是 `Message -> MessageExt -> MessageExtBrokerInner` 的分层对象链。
- `Message` 负责业务语义和属性；`MessageExt` 增加 Broker 存储与投递元数据；`MessageExtBrokerInner` 才是进入 Broker 编码与落盘链路的内部对象。
- 很多高级语义并不是单独字段，而是落在 `properties` 里，例如 `TIMER_DELIVER_MS`、`TRANSACTION_PREPARED`、`SHARDING_KEY`、`LITE_TOPIC`。
- `MessageVersion` 在 5.5.0 里最关键的差异不是“协议大改”，而是 topic 长度字段从 1 字节扩展到了 2 字节。
- CommitLog 里保存的是编码后的完整消息；ConsumeQueue 只保留 `commitlog offset + size + tagsCode`，不会重复存消息体。

## 先把对象层级拆开

### 1. [[01-RocketMQ 5.x架构与领域模型总览]]`Message`

这是客户端最基础的业务消息对象，核心字段只有：

- `topic`
- `flag`
- `properties`
- `body`
- `transactionId`

源码里很多常见能力其实都只是 `properties` 的语法糖：

```java
public void setTags(String tags) {
    putProperty(MessageConst.PROPERTY_TAGS, tags);
}

public void setKeys(String keys) {
    putProperty(MessageConst.PROPERTY_KEYS, keys);
}

public void setDelayTimeLevel(int level) {
    this.putProperty(MessageConst.PROPERTY_DELAY_TIME_LEVEL, String.valueOf(level));
}

public void setDeliverTimeMs(long timeMs) {
    this.putProperty(MessageConst.PROPERTY_TIMER_DELIVER_MS, String.valueOf(timeMs));
}
```

所以第一层事实是：

- RocketMQ 的“消息类型扩展”大量依赖属性系统，而不是不断给 `Message` 增字段。

### 2. [[04-Topic与消息类型约束]]`MessageExt`

`MessageExt` 是“进入 Broker 之后的扩展消息”。

它新增的是运行时和存储定位信息：

- `queueId`
- `queueOffset`
- `sysFlag`
- `bornTimestamp` / `bornHost`
- `storeTimestamp` / `storeHost`
- `msgId`
- `commitLogOffset`
- `reconsumeTimes`
- `preparedTransactionOffset`

这层的重点不是业务字段，而是：

- 这个消息被放到了哪个逻辑队列
- 在 commitlog 里的物理位置是什么
- 是否是压缩 / 事务 / 批量消息

### 3. [[28-CommitLog写入流程]]`MessageExtBrokerInner`

这是 Broker 真正写入存储前使用的内部对象。

它新增了几个关键字段：

- `propertiesString`
- `tagsCode`
- `encodedBuff`
- `version`

这几个字段分别对应：

- 属性 map 的序列化结果
- ConsumeQueue 过滤使用的 tag 哈希
- 预编码缓存
- CommitLog 编码版本

所以如果只停留在 `MessageExt`，你会漏掉 Broker 落盘前真正依赖的编码信息。

### 4. [[43-消息压缩机制]] `MessageBatch` / `MessageExtBatch`

这里最容易混淆。

- `MessageBatch` 是客户端侧的批量容器，继承自 `Message`
- `MessageExtBatch` 是 Broker 存储链上的批量内部对象，继承自 `MessageExtBrokerInner`

`MessageBatch.generateFromList(...)` 会校验：

- topic 必须一致
- `waitStoreMsgOK` 必须一致
- 不允许再带 delay level

这说明批量消息不是“把几条消息随便拼起来”，而是受严格约束的单次发送载体。

## 消息属性系统才是很多高级特性的真实承载面

`MessageConst` 里定义了大量系统属性。研究时建议按语义分组，而不是背全表。

### 业务定位类

- `PROPERTY_KEYS`
- `PROPERTY_TAGS`
- `PROPERTY_UNIQ_CLIENT_MESSAGE_ID_KEYIDX`

### 延迟 / 定时类

- `PROPERTY_DELAY_TIME_LEVEL`
- `PROPERTY_TIMER_DELAY_SEC`
- `PROPERTY_TIMER_DELAY_MS`
- `PROPERTY_TIMER_DELIVER_MS`

### 事务类

- `PROPERTY_TRANSACTION_PREPARED`
- `PROPERTY_CHECK_IMMUNITY_TIME_IN_SECONDS`
- `PROPERTY_REAL_TOPIC`
- `PROPERTY_REAL_QUEUE_ID`

### 消费与重试类

- `PROPERTY_RETRY_TOPIC`
- `PROPERTY_RECONSUME_TIME`
- `PROPERTY_MAX_RECONSUME_TIMES`
- `PROPERTY_CONSUME_START_TIMESTAMP`

### 5.x / 特性类

- `PROPERTY_SHARDING_KEY`
- `PROPERTY_LITE_TOPIC`
- `PROPERTY_PRIORITY`

这也是为什么很多 5.x 语义最好从 `properties` 入手理解，而不是先找某个“专用字段”。

## `sysFlag` 解决的是“需要位图快速判断”的能力

和属性系统不同，`sysFlag` 用来保存需要在存储和解码链快速判断的状态。

典型包括：

- 是否压缩
- 压缩算法类型
- 是否事务 prepared
- 是否批量消息

它和 `properties` 的分工可以这样理解：

- `properties` 负责语义承载与扩展
- `sysFlag` 负责高频、固定格式、解码敏感的位状态

## CommitLog 编码不是照着对象字段顺序直接序列化

`MessageDecoder` / CommitLog 编码链里，消息会被整理成固定头部 + 变长体的结构。

可以把它压缩理解成：

1. [[01-RocketMQ 5.x架构与领域模型总览]]固定头部
2. [[04-Topic与消息类型约束]]body
3. [[28-CommitLog写入流程]]topic
4. [[43-消息压缩机制]] propertiesString

这里几个最关键的字段是：

- `TOTAL_SIZE`
- `MAGIC_CODE`
- `BODY_CRC`
- `QUEUE_ID`
- `QUEUE_OFFSET`
- `PHYSICAL_OFFSET`
- `SYS_FLAG`
- `STORE_TIMESTAMP`
- `BODY_LENGTH`
- `TOPIC_LENGTH`
- `PROPERTIES_LENGTH`

研究时真正该记住的是三个点：

- CommitLog 里保存的是完整消息快照
- topic 和 properties 都是变长字段
- 解码时要先靠 `MAGIC_CODE` 反推出 `MessageVersion`

## `MessageVersion` 在 5.5.0 的真实作用

旧稿里最容易把它写成“兼容多个协议版本”的泛泛说法，但源码里最关键的差异其实很具体。

`MessageVersion` 只有两个枚举：

- `MESSAGE_VERSION_V1`
- `MESSAGE_VERSION_V2`

它们最重要的区别是 topic 长度字段：

```java
MESSAGE_VERSION_V1 {
    public int getTopicLengthSize() { return 1; }
}

MESSAGE_VERSION_V2 {
    public int getTopicLengthSize() { return 2; }
}
```

也就是：

- V1 用 1 字节保存 topic 长度
- V2 用 2 字节保存 topic 长度

这意味着 `MessageVersion` 不是一个“到处散发能力差异”的大体系，而是编码层的精确兼容点。

## 消息在不同层的形态变化

可以把同一条消息看成四个阶段：

### 阶段 1：客户端业务对象

`Message`

只关心：

- topic
- body
- tags/keys/自定义属性

### 阶段 2：发送前增强

客户端或 Proxy 会补：

- uniqKey
- 延迟属性
- 事务属性
- shardingKey
- liteTopic

### 阶段 3：Broker 内部消息

`MessageExtBrokerInner`

会补：

- queueId / queueOffset
- tagsCode
- propertiesString
- version

### 阶段 4：存储格式

CommitLog 二进制记录 + ConsumeQueue 20 字节索引

研究消息系统时，很多“为什么这个字段读不到/为什么这里不是原值”的问题，都出在这四层被混看了。

## 容易误解的点

### `properties` 不是“用户属性专属区域”

RocketMQ 的系统语义大量也在 `properties` 里。

所以：

- 自定义属性要避开系统保留 key
- 分析消息类型时要先看属性，不要只看 class

### `MessageExt` 不是存储最终形态

它只是更贴近运行时的对象；真正写入 CommitLog 的仍是编码后的二进制结构。

### `tagsCode` 不是完整 Tag

它只是为了 ConsumeQueue 快速过滤准备的哈希或扩展地址，不等于完整属性字符串。

### 批量消息不是 Broker 自动聚合

客户端侧已经先做了批量封装和约束校验。
