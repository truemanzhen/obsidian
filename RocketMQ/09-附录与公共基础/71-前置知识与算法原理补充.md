## 1. Reactor 与 Epoll

RocketMQ 的 remoting 层并不是“一个连接一个线程”，而是典型 Reactor 模型：

- accept 线程
- I/O event loop
- 业务处理线程池

对应代码主要在：

- `NettyRemotingServer`
- `NettyRemotingClient`
- `DefaultEventExecutorGroup`

为什么这对 RocketMQ 重要：

- Broker/NameServer/Controller 都要承载大量短连接和高频心跳
- 如果用 thread-per-connection，线程数和上下文切换会直接失控

## 2. Raft、Term/Epoch、脑裂防护

RocketMQ 5.5.0 里至少有两条地方会用到“任期/epoch”思维：

- Controller 侧的选主与副本集元数据
- AutoSwitchHA / DLedger 的主从切换与截断

源码锚点：

- `controller/.../ReplicasInfoManager.electMaster(...)`
- `store/.../ha/autoswitch/EpochFileCache`
- `store/.../ha/autoswitch/AutoSwitchHAService`

这里最关键的不是背 Raft 定义，而是理解：

- 为什么换主之后要递增 master epoch
- 为什么要根据 epoch 找一致点并截断脏数据

## 3. WAL：为什么所有消息先写 CommitLog

RocketMQ 的典型 WAL 体现就是：

- 先顺序 append 到 `CommitLog`
- 再异步分发到 `ConsumeQueue` / `IndexFile` / 其他派生结构

源码锚点：

- `CommitLog.asyncPutMessage(...)`
- `DefaultMessageStore.ReputMessageService`

这个设计解决的是：

- 顺序写吞吐
- 崩溃恢复时以 CommitLog 为主真相源

## 4. mmap 与页缓存

RocketMQ 没有直接手写一套块设备 I/O，而是围绕 `MappedFile` 使用 mmap。

源码锚点：

- `MappedFile`
- `MappedFileQueue`
- `TransientStorePool`

你真正需要记住的是：

- RocketMQ 写的先是内存映射区，不等于立刻落盘
- `flush` 和 `commit` 解决的是不同层面的持久化推进

## 5. LSM-Tree / RocksDB

RocksDB 引入后，RocketMQ 并不是把所有消息正文直接丢进 RocksDB。

当前 5.5.0 更关键的落点是：

- `RocksDBConsumeQueueStore`
- `IndexRocksDBStore`
- `TransMessageRocksDBStore`
- `TimerMessageRocksDBStore`

它回答的是：

- 哪些原本靠文件顺序追加的辅助结构，开始改成 KV/LSM 组织

## 6. 时间轮

延迟消息的 5.x 语义最终落到：

- `TimerMessageStore`
- `TimerLog`
- `TimerWheel`
- `TimerCheckpoint`

时间轮在这里不是教科书插图，而是 Broker 侧决定“某个时刻该取哪些延迟消息出队”的关键索引。

## 7. Log Compaction

`CompactionStore` 本质上是：

- 按业务 key 汇总多次更新
- 只保留某个 key 的较新值

它和普通消息顺序消费不是一个优化目标。

源码锚点：

- `CompactionService`
- `CompactionLog`
- `CommitLogDispatcherCompaction`

## 8. HMAC

ACL 里的签名校验并不是 RocketMQ 自创算法，而是典型：

- 请求内容 canonicalize
- secret 参与 HMAC
- Broker 校验签名与资源权限

源码对应  即可，不需要在这里扩写成密码学笔记。

## 9. 一致性 Hash

在 RocketMQ 5.5.0 里，一致性 Hash 最直接的落点不是 Rebalance，而是 FIFO / Lite 分片路由：

- `SendMessageActivity.SendMessageQueueSelector`
- `LiteShardingImpl`

例如 Proxy 发送 FIFO 消息时：

```java
int bucket = Hashing.consistentHash(shardingKey.hashCode(), writeQueues.size());
```

它解决的是：

- 相同 message group 尽量落到同一 queue
- queue 数量变化时减少整体重映射

## 10. Bitmap

POP / revive 这条线里，Broker 不可能为每个未 ack 消息都维护一套昂贵对象图。

因此需要：

- checkpoint
- ack/batch-ack 事件
- 位图或等效压缩表示

源码锚点：

- `PopCheckPoint`
- `AckMsg`
- `BatchAckMsg`
- `PopReviveService`

这里的重点不是泛泛理解 bitmap，而是理解：

- 为什么 revive 扫描不是简单按 offset 重放

## 11. 这篇要补的源码对照观念

很多“底层原理”在 RocketMQ 里不是抽象背景，而是直接进入状态对象：

- Epoch 落到 `EpochFileCache`
- namespace 落到 `NamespaceUtil`
- request mode 落到 `MessageRequestModeManager`
- FIFO 落到 `PROPERTY_SHARDING_KEY`、客户端锁、POP orderly 管理器

所以研究时最稳的姿势是：

1. 先识别概念
2. 再找 RocketMQ 里的承载对象
3. 最后回到具体主链
