# 5.x 消费模型与负载均衡

> 研究定位：把 5.x 的消费模型从“Push / Pull 二选一”升级成“客户端模型 + Broker 请求模式 + 负载均衡策略”的三层结构。
> 关键源码：`MessageRequestModeManager`、`QueryAssignmentProcessor`、`RebalanceImpl`、`RouteActivity.queryAssignment(...)`
> 阅读建议：先把“API 模型”和“Broker 请求模式”分开，再看 assignment / rebalance 谁在做决定。

## 为什么这一篇不能和 Rebalance 混在一起

- 旧版本里常见的理解是：消费模型 = Push / Pull，负载均衡 = Rebalance。
- 5.5.0 里，这个理解已经不够了。
- 现在至少要同时区分：
- 客户端 API 模型
- Broker 侧 `MessageRequestMode`
- 负载均衡 / assignment 的实现方式

## 先给结论

- `Push` / `Pull` / `LitePull` 是客户端 API 风格。
- `PULL` / `POP` 是 Broker 侧消息请求模式。
- `RebalanceImpl` 是经典 Java Client 里的队列分配骨架。
- `QueryAssignmentProcessor` / `RouteActivity` 则代表了 Broker / Proxy 参与 assignment 的 5.x 路径。
- `LITE_PUSH_CONSUMER` 和 `SIMPLE_CONSUMER` 是协议侧客户端类型，不是 `MessageRequestMode` 枚举值。

## 5.x 至少有三种“消费模型”视角

### 1. 经典 Java Client 视角

- `DefaultMQPushConsumer`
- `DefaultMQPullConsumer`
- `DefaultLitePullConsumer`

### 2. Broker 请求模式视角

- `MessageRequestMode.PULL`
- `MessageRequestMode.POP`

这层配置由 `MessageRequestModeManager` 以 `topic -> consumerGroup -> requestBody` 的形式持久化。

这里要特别纠正一个容易混淆的点：

- `MessageRequestMode` 枚举只有 `PULL` 和 `POP`
- 没有 `LITE_PULL`

`LitePull` 是客户端 API / 使用模型，不是 broker 侧请求模式枚举值。

### 3. gRPC / Proxy 协议视角

- `PUSH_CONSUMER`
- `LITE_PUSH_CONSUMER`
- `SIMPLE_CONSUMER`

## 负载均衡也分两类

### 1. 经典客户端 Rebalance

对应实现树：

- `RebalanceImpl`
- `RebalancePushImpl`
- `RebalanceLitePullImpl`

分配策略包括：

- `AllocateMessageQueueAveragely`
- `AllocateMessageQueueAveragelyByCircle`
- `AllocateMessageQueueConsistentHash`

### 2. 5.x 的 Assignment 路径

Broker / Proxy 侧会参与：

- `QueryAssignmentProcessor`
- `RouteActivity.queryAssignment(...)`

这里已经不只是“客户端本地算一遍队列归属”，而是服务端参与了消费模式和 assignment 结果的协商。

`QueryAssignmentProcessor` 的真实流程是：

- 从 `MessageRequestModeManager` 里读 `topic + consumerGroup` 的请求模式
- 没配置时：
  - retry topic 强制 `PULL`
  - 普通 topic 走 broker 默认 `defaultMessageRequestMode`
- 如果模式是 `POP`，还会带上 `defaultPopShareQueueNum`

## Pop 模式为什么会改变负载均衡语义

`POP` 和传统 `PULL` 的一个关键差异是：

- 不是简单“每个 client 固定拉自己的 queue”
- 而是会引入 `popShareQueueNum`、retry topic、revive 等新的调度要素

源码里的 `allocate4Pop(...)` 还定义了两个很关键的分支：

- `popShareQueueNum <= 0` 或过大时，每个 client 都可能共享全部 queue
- 否则会在经典分配结果基础上，再额外共享后续若干 consumer 的 queue

这就是 POP 和传统 rebalance 在“队列所有权”语义上的根本差异。

## 服务端负载均衡不是总会参与

`QueryAssignmentProcessor` 里还有一个边界：

- 如果 `serverLoadBalancerEnable == false`
- 直接返回 topic 的全部订阅队列集合

所以研究时要区分：

- “服务端参与 assignment 的能力存在”
- 和“当前 broker 配置一定启用了服务端负载均衡”

这是两回事。

所以：

- 不能把 `POP` 简单理解为“Pull 的另一种 API”
- 它会反过来影响 assignment、重试 topic、Ack 以及消费公平性
