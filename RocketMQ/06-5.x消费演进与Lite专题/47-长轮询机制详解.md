# 长轮询机制详解

> 研究定位：把 RocketMQ 的“看起来像推送”的实时消费体验拆到 Pull 挂起、POP 挂起、LitePush 通知三条后台等待链。
> 关键源码：`broker/longpolling/PullRequestHoldService.java`、`broker/longpolling/PopLongPollingService.java`、`broker/longpolling/PopLiteLongPollingService.java`、`broker/longpolling/NotifyMessageArrivingListener.java`、`broker/processor/NotificationProcessor.java`
> 阅读建议：先看 [[46-Push消费与Pull消费]] 和 [[48-Pop消费模式详解]]，因为长轮询本质上是这些消费模型在 broker 侧的等待机制。

## 先给结论

- RocketMQ 没有“Broker 直接 server push 业务消息”这条经典主线；Push、POP、LitePush 的实时性都建立在长轮询挂起与唤醒之上。
- 经典 Pull/Push 的长轮询核心是 `PullRequestHoldService`，按 `topic@queueId` 挂请求。
- POP 的长轮询核心是 `PopLongPollingService`，按 `topic@cid@queueId` 挂请求，并且会联动 POP retry topic。
- LitePush 不是复用 `PullRequestHoldService`，而是通过 `NotificationProcessor -> PopLongPollingService` 以及 `PopLiteLongPollingService` / Lite 事件分发协同完成通知。
- `NotifyMessageArrivingListener` 是消息到达后的统一入口，但它会先分流 LiteTopic，再分别通知 Pull、POP 和 Notification 三条路径。

## 长轮询在 RocketMQ 里到底解决什么问题

如果 broker 没消息就立刻返回空响应，客户端只能短轮询：

- 请求频繁
- 空转严重
- 实时性差

RocketMQ 的做法是：

```text
请求先挂起
  -> 新消息到达时唤醒
  -> 如果等到超时还没有消息，再返回空结果
```

所以长轮询不是“新协议”，而是 broker 侧对 Pull/POP 请求的等待策略。

## 经典 Pull/Push：PullRequestHoldService

### 挂起粒度

`PullRequestHoldService` 的表结构是：

```java
ConcurrentMap<String/* topic@queueId */, ManyPullRequest> pullRequestTable
```

这说明经典 Pull 的等待粒度是：

- topic
- queueId

而不是 consumer group 级别的更细粒度等待。

### 请求何时挂起

当 `PullMessageProcessor` 发现当前没有可返回消息，但又允许长轮询时，会把请求交给：

```java
pullRequestHoldService.suspendPullRequest(topic, queueId, pullRequest)
```

被挂起的请求会被标记：

```java
pullRequest.getRequestCommand().setSuspended(true);
```

### 唤醒条件

`notifyMessageArriving(...)` 会把同一 `topic@queueId` 下挂起的请求拿出来，逐个判断：

- 当前 `maxOffset` 是否已经大于请求的 `pullFromThisOffset`
- 过滤条件是否匹配
- 是否已经超时

满足任一可返回条件，就执行：

```java
pullMessageProcessor.executeRequestWhenWakeup(...)
```

否则会重新放回 `replayList`。

这说明经典长轮询不是“来一条消息就全部叫醒”，而是：

- 先看 offset 是否推进
- 再看 broker 侧过滤是否通过
- 不满足则继续挂着

## `Push` 为什么本质还是 Pull

PushConsumer 在客户端看起来像回调消费，但 broker 侧仍然只看得到 Pull 请求。

因此：

- Push 的长轮询服务并不是单独一套 “PushHoldService”
- 它复用的仍是 `PullRequestHoldService`

这也是 [[46-Push消费与Pull消费]] 那篇必须放在本篇之前读的原因。

## POP：PopLongPollingService

### 挂起粒度更细

`PopLongPollingService` 的核心表结构是：

```java
Cache<String, ConcurrentSkipListSet<PopRequest>> pollingMap;
Cache<String, ConcurrentHashMap<String, Byte>> topicCidMap;
```

其中 key 来自：

```java
KeyBuilder.buildPollingKey(topic, cid, queueId)
```

也就是：

- topic
- consumer group / cid
- queueId

比经典 Pull 多了一层 group 维度。

### 为什么 POP 需要更细粒度

因为 POP 不只是“等新消息”，它还要处理：

- 正常 topic
- retry topic
- group 级消费状态
- share queue 语义

所以它不能只按 `topic@queueId` 粗粒度挂请求。

### 超时扫描

`PopLongPollingService.run()` 每 20ms 检查一轮：

```java
this.waitForRunning(20);
```

它会从每个 `ConcurrentSkipListSet<PopRequest>` 里拿最早超时的请求：

- 未超时则放回去
- 已超时则 `wakeUp(first)`

所以 POP 的等待检查比经典 Pull 更高频，也更依赖内存结构性能。

### 消息到达后的唤醒

`notifyMessageArriving(...)` 会：

1. 从 `pollingMap` 里拿到对应 `topic@cid@queueId` 的等待集合
2. 取一个 `PopRequest`
3. [[51-MessageRequestModeManager]]用 `MessageFilter` 做 broker 侧过滤
4. [[48-Pop消费模式详解]]匹配则 `wakeUp(popRequest)`
5. 不匹配则塞回集合继续等

所以 POP 的长轮询也不是单纯“消息来了就返回”，而是先做 broker 侧筛选。

## POP 会连带处理 retry topic

`notifyMessageArrivingWithRetryTopic(...)` 里有显式分支：

```java
if (NamespaceUtil.isRetryTopic(topic)) {
    notifyMessageArrivingFromRetry(...)
} else {
    notifyMessageArriving(...)
}
```

这说明 POP 长轮询并不是只监听正常 topic。

当新消息写到 POP retry topic 时，它也能反向唤醒挂起请求，把这批消息继续交给 POP 消费链处理。

这就是 POP 长轮询比经典 Pull 更复杂的一个核心原因。

## LitePush / Notification 不是另一套 Pull hold

`NotificationProcessor` 内部自己持有一个：

```java
private final PopLongPollingService popLongPollingService;
```

它的职责不是直接返回消息，而是先回答“有没有消息”，必要时进入 polling。

当没有消息时：

```java
PollingResult pollingResult = popLongPollingService.polling(...)
```

这说明 5.x Notification / LitePush 的等待语义，本质上也站在 POP 风格的 polling 服务之上，而不是走经典 `PullRequestHoldService`。

## PopLiteLongPollingService 与 Lite 事件分发

5.5.0 里还有一条 Lite 专用的等待服务：

- `PopLiteLongPollingService`

它的 key 粒度是：

- `clientId`
- `group`

而不是普通 POP 的 `topic@cid@queueId`。

另外 `NotifyMessageArrivingListener` 对 LiteTopic 还会先做一次特殊分流：

```java
if (LiteUtil.isLiteTopicQueue(topic)) {
    this.liteEventDispatcher.dispatch(null, topic, queueId, logicOffset, msgStoreTime);
    return;
}
```

这说明：

- LiteTopic/LitePush 有一层独立事件分发语义
- 普通 topic 才继续走 Pull / POP / Notification 三连通知

所以不要把 “LitePush 长轮询” 和 “LiteTopic 事件分发” 混成一个点。

## NotifyMessageArrivingListener：统一入口，但不是统一实现

`NotifyMessageArrivingListener.arriving(...)` 的真实逻辑是：

1. 如果是 LiteTopic 队列，直接交给 `liteEventDispatcher`
2. 否则通知：
   - `pullRequestHoldService`
   - `popMessageProcessor`
   - `notificationProcessor`

也就是说它的统一，只体现在“消息到达统一入栈”：

- 统一入口
- 分别唤醒

它并没有把三种等待机制合并成一套数据结构。

## 这篇要纠正的几个旧说法

- “Push 有自己独立的 broker 推送线程。”  
  经典 Push 仍是 Pull 请求 + `PullRequestHoldService`。

- “长轮询只有一套实现。”  
  至少要区分 Pull、POP、Notification/Lite 的等待结构。

- “NotifyMessageArrivingListener 只负责 Pull。”  
  它还会通知 POP、Notification，并对 LiteTopic 先做单独分流。

- “POP 长轮询只关心正常 topic。”  
  它还显式处理 retry topic 唤醒。
